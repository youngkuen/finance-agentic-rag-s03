# ADR-002. 인제스천에 LangGraph 를 쓰되, 문서당 LLM 루프는 두지 않는다

- 상태: 채택
- 날짜: 2026-10-02
- 관련: ADR-001, `src/finrag/ingestion/graph.py`

---

## 맥락

**무엇이 문제였나.** 2회차까지 파싱·검사·청킹은 돌아갔지만 셋이 따로 놀았다. 문서 한 건이
어디서 걸렸는지 알려면 로그를 뒤져야 했고, 깨진 PDF 를 다른 파서로 다시 뽑는 복구 경로는
스크립트 안에 if 문으로 숨어 있었다. 코퍼스 51건 중 2건은 아예 형식이 지원되지 않고, 1건은
어떤 파서로도 쓸 수 있는 페이지가 나오지 않는다. 이 3건을 조용히 버리면 "검색이 못 찾는 것"과
"애초에 안 들어간 것"을 구분할 수 없다.

측정된 사실:

| 무엇 | 값 | 출처 |
|---|---|---|
| 처리 문서 수 | 49건 → 청크 3,695개 | `data/ingest_report.json` |
| 게이트 판정 분포 | pass 40 · reparse 5 · ocr 2 · fail 2 | `data/ingest_report.json` |
| 사람 검토 큐 | 3건 (done 46 / failed 3) | `data/ingest_report.json` |
| 인제스천 LLM 호출 | 0회 (정상 경로) | `data/ingest_report.json` 의 `llm_repaired: []` |
| 첫 검색 성능 | Recall@5 0.775 · MRR 0.555 | `results/baseline.json` |

사람 검토 큐 3건의 내역과 원인:

| 문서 | 이유 | 어느 갈래로 왔나 |
|---|---|---|
| `law_silson_std_hwp` | 지원하지 않는 형식(office) | 게이트 이전, `classify` 가 office 로 판정 |
| `fss_deposit_terms_2022_hwpx` | 지원하지 않는 형식(office) | 위와 같음 |
| `knia_4000` | 재추출 필요 1쪽 · 쓸 수 있는 페이지가 없음 | gate → reparse → llm_repair → LLM 키 없음 → dead_letter |

앞의 둘은 **형식 때문에 못 읽은 것**이고 `knia_4000` 은 **글자가 깨진 것**이다. 원인이 다르면
대응도 다르다(전자는 변환기 도입, 후자는 OCR·LLM 복구). 큐에서 이 둘이 섞이면 둘 다 못 고친다.

## 대안

| # | 대안 | 장점 | 단점 | 왜 안 골랐나 |
|---|---|---|---|---|
| A | 문서마다 LLM 에게 읽혀서 정리시킨다 | 파서 품질 편차를 모델이 흡수. 코드가 짧다 | 문서 51건마다 호출 → 비용·지연이 문서 수에 비례. 같은 입력에 다른 출력 | 비용·지연·재현성을 한꺼번에 잃는다. 게다가 **모델이 약관 조항을 그럴듯하게 지어내면 그게 근거로 인용된다.** 금융 문서에서 이건 품질 문제가 아니라 사고다 |
| B | if 문으로 직접 짠다 (2회차 방식의 연장) | 의존성이 늘지 않는다. 당장 제일 빠르다 | 분기가 4개에서 멈추지 않는다. 문서가 어느 경로로 갔는지는 로그를 파싱해야 안다. 재실행 시 처음부터 | 리포트를 매번 손으로 짜게 된다. 4회차부터 검색·재랭킹이 이 위에 얹히면 분기가 더 늘어난다 |
| C | **LangGraph 로 제어흐름만 세우고 LLM 은 실패 브랜치에만 둔다** | 경로가 상태로 남아 리포트가 공짜. 조건부 엣지로 분기가 선언적. `thread_id` 체크포인트로 재실행이 멱등 | 의존성 하나 추가. 그래프 구조를 익혀야 한다 | **← 골랐다** |

## 결정

> 인제스천은 결정적 파이프라인(classify → parse → gate → chunk)으로 세우고, LLM 은
> `llm_repair` 단 하나의 노드에만 둔다. 그 노드는 다른 파서로 재추출해도 쓸 수 있는 페이지가
> **0개일 때만** 호출한다(`route_after_reparse` 의 `usable_pages == 0` 조건).

정상 경로에서 LLM 호출은 0회다. 이번 실행에서도 `llm_repaired` 는 빈 목록이다.

## 근거 지표

| 지표 | 전 (2회차, 스크립트) | 후 (3회차, 그래프) | 차이 |
|---|---|---|---|
| 문서당 LLM 호출 | 해당 없음 (LLM 미사용) | 0회 (복구 경로만 최대 1회) | 유지 |
| 문서 경로 추적 | 로그 수동 확인 | `ingest_report.json` 자동 생성 | 리포트 공짜 |
| 게이트 판정 종류 | pass/fail 2종 | pass·reparse·ocr·fail 4종 | +2 |
| Recall@5 | 측정하지 않았다 | 0.775 | 최초 측정 |
| MRR | 측정하지 않았다 | 0.555 | 최초 측정 |

측정 방법: `골든셋 40문항 · Dense 검색(BGE-M3, 1024차원) · Qdrant 임베디드 모드`
재현 명령: `make ingest && make index && make baseline && make check-s03`

## 대가

| 잃은 것 | 얼마나 | 받아들일 만한 이유 |
|---|---|---|
| 의존성 추가 (langgraph) | 패키지 1개 | 분기가 4개를 넘는 순간 if 문보다 읽기 쉽다. 4회차부터 검색이 이 위에 얹힌다 |
| 깨진 페이지를 지우지 않고 색인 | 품질 낮은 5건(reparse)이 그대로 들어감 | 지우면 아무것도 못 찾지만, 두면 임베딩은 여전히 찾아낸다. `meta.degraded_pages` 로 나중에 분리 가능 |
| 형식 미지원 문서는 손도 못 댐 | 2건 (hwp/hwpx) | 변환기 도입은 별도 결정. 지금은 큐에 **이유와 함께** 남겨 두는 것으로 충분 |
| 학습 비용 | 그래프 구조 이해 1회 | 한 번만 치르면 된다 |

## 되돌릴 조건

- [ ] `Recall@5` 지표가 `0.60` 아래로 내려가면 (파서 품질이 원인인지부터 본다)
- [ ] `사람 검토 큐` 가 `전체 문서의 10%` 를 넘으면 (지금 3/49 = 6.1%)
- [ ] 문서 수가 `500건` 를 넘으면 (순차 실행 6분 → 1시간. 병렬 실행이나 큐 도입을 검토)
- [ ] 깨진 문서 비율이 급증해 `llm_repair` 호출이 전체의 5% 를 넘으면 — 그때는 "문서당 LLM"이
      아니라 **파서 교체**나 **원본 수급 경로 변경**을 먼저 본다
- [ ] hwp/hwpx 변환기(예: hwp5txt)가 안정화되면 — 사람 검토 큐 3건 중 2건이 바로 사라진다

되돌리는 비용: 그래프 → 스크립트 회귀는 `graph.py` 한 파일(약 40줄). 인덱스 재생성은 임베딩
스냅샷이 있으면 14초, 없으면 25분. 코드 변경은 `pipelines/ingest.py` 의 호출부 한 줄.

## 결과

결정을 적용한 뒤 실제로 어떻게 됐나. **나중에 채운다.**

3회차 시점: 문서 49건이 네 갈래로 갈려 46건이 색인되고 3건이 이유와 함께 큐에 남았다.
첫 검색 성능은 Recall@5 0.775 · MRR 0.555. 다만 유형별로 보면 계산형 0.600 · 미답변형 0.000 으로
평균이 가리는 구멍이 있다. 4회차의 검색 개선이 이 구멍을 메우는지를 같은 지표로 다시 본다.
